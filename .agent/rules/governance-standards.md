# 專案治理標準 (Governance Standards)

本文件正式化了專案管理與協作的核心原則，旨在確保開發軌跡透明、文檔與代碼同步，以及系統的高度安全性。

---

## 1. 原子化文檔同步 (Atomic-Wiki-Sync - Rule #12)

為了防止「文檔過時 (Doc-Rot)」，本專案執行嚴格的原子化同步原則：

- **同步義務**: 任何涉及架構設計、核心流程或 API 變動的開發任務，必須在同一個 commit 或同一個開發週期內同步更新對應的 Wiki 文檔。
- **Git 提交規範**: 遵循 `git-commit-format.md`，提交訊息必須包含雙語描述，且明確標註是否包含文檔更新。
- **CI 檢查**: CI Pipeline 會定期掃描文檔完整性與連結正確性，不符合標準的文檔變更將被標示為失敗。

## 2. 敏感資訊零容忍 (No-Hardcoded-Secrets - Rule #13)

資安是系統的底線，嚴禁任何形式的憑證洩漏：

- **零硬編碼**: 嚴禁在代碼中、甚至是 `tests/` 或 `Archive/` 目錄下硬編碼 API Key、密碼或 PII (個人身分資訊)。
- **環境變數導向**: 所有配置必須透過執行期環境變數、`.env` 文件（嚴禁提交）或加密儲存區獲取。
- **自動化掃描**: 專案整合了 `bandit` 與 `secret-scanning` 工具。若 CI 偵測到疑似憑證的字串，建置流程將立即終止。

## 4. DB 集中管理與 UI 操作原則 (DB-Managed Settings - Rule #14)

為了確保系統的可維護性與動態調整能力：

- **DB 優先**: 所有可啟用的功能、系統閾值、API 金鑰或管道配置，應優先存放於資料庫（`settings` 表）中，而非寫死在代碼或全域環境變數中。
- **UI 管理**: 所有存放於 DB 的設定，必須在 Dashboard 中提供對應的介面進行操作（如 `SettingsService` 整合），確保非開發人員亦可安全調整系統行為。
- **動態載入**: 系統在啟動或執行期應透過 `SettingsService` 動態獲取配置，確保變更能即時生效（或僅需服務重啟）。

---
*違反上述標準將被視為重大代碼質量缺陷，必須於 PR 合併前修復。*
