# DD-2026-1030 — K1 成本比率與 LLM 年預算互相卡住（提案，待人裁決）
> 一句話：`mission.yaml` 的 LLM 年預算上限約等於 K1 在目前淨值下的損益兩平，預算用滿就等於 K1 違規。回放顯示解除日對每日花費極敏感：每日 $0.135 以下才會解除，以上永遠不解除。這份文件列出三案與後果，不改 `mission.yaml`。

**狀態**：提案（未實作）
**風險級**：R3 提案（`config/mission.yaml` 的 `budgets`、`kill_criteria`）；本文件是 R0。
**上游**：ADR-003 (5)；DD-2026-1029 §5（K1 另案）；使用者 2026-10-30 決定「先出回放數據，不改 mission.yaml」

## 1 矛盾在哪

- K1 ＝（近 30 日計費 LLM 成本 × 365/30 ＋ 訂閱 × 12）÷ NAV，門檻 3%（`config/mission.yaml` `kill_criteria`）。
- 預算 `max_llm_usd_per_year` 與 `max_total_cost_pct_of_nav`（LLM＋資料＋手續費，3%）並存。
- 淨值約 $1650 時，3% 約 $49.4／年，已經低於或等於 LLM 預算上限。預算用滿，K1 就違規，資料與手續費還沒算。
- 本文件的數字是 2026-10-30 當日快照，會漂移，以指令為準。

## 2 回放（唯讀，可重跑）

2026-10-30 的結果（月訂閱假設 0，**未驗證**，見 §5）：

| 情境 | 每日花費 | 年化 | K1 解除日 |

| 近 7 日均（watchdog 用的） | 約 $0.14 | 約 $50 | 2026-11-27 |

- 目前 K1 約為門檻的三倍（近 30 日計費約 $13，換算約 9.8%）。
- 損益兩平每日花費約 $0.135（＝3%×NAV÷365）。比它高，穩態下 K1 就回不到 3% 以下。
- 近 7 日均剛好略高於兩平。它顯示 11-27 解除，是因為今日 10-30 還沒入帳（算 0）加上窗口內最近幾天偏低；花費維持目前水準，這個日期會往後掉，不是穩定的預測。[推論，依 `k1_projection.py` 的窗口定義]
- 10-09 到 10-16 單日花費 $0.85–1.4，之後降到 $0.04–0.7；降下來的原因沒查。

## 3 三案

| | A：調高 K1 門檻或預算結構 | B：壓低 LLM 花費 | C：接受 K1 結構性違規 |
|---|---|---|---|
| 做法 | 改 K1 門檻，或把 LLM 預算拆出 K1（例如 K1 只算實付總成本，預算改以絕對金額管） | 把每日花費壓在兩平之下並留餘裕給資料與手續費：降 agent 頻率、改低階模型 | 不動，K1 在凍結原因裡長期存在 |
| 後果 | 解凍條件放寬，等於調整憲章；需 ADR。門檻放寬後 K1 失去「成本壓過可賺空間」的警示力 | 解除日可預期（固定 $0.10 約 11-20，與 K3／K4 的 11-19 同期）。代價是分析品質與覆蓋下降，進化迴圈的實驗量也受限 | 凍結只因 K1 持續；NAV 長到 $50÷3% ≈ $1670 以上才有空間，但幾乎沒有餘裕。實務上系統長期凍結或在邊緣反覆 |
| 風險級 | R3（改 `mission.yaml`） | R2（設定、tier 路由；動 LLM 預算設定） | R0（不動） |
| 不可逆性 | 可還原，但每次放寬都是先例 | 可還原 | 可還原，但持續凍結本身有成本 |

我的看法（判斷，不是從資料推出來的）：B 最符合憲章原意，因為 K1 的設計目的就是讓成本不吞掉可賺空間；A 是在證據不足時放寬安全閘門，與「放寬前先查影響」的原則相反。C 在淨值遠小於預算時等於把系統鎖死。B 要與進化迴圈的實驗成本一起看，不能單獨砍。

## 5 已查到的與沒查到的（2026-10-30 補查）

**月訂閱成本：已確認為 0。** `settings` 表 `monthly_data_subscription_cost_usd` 的值是明確設定的 `0.0`，不是缺值。回放以 0 計成立。但這是使用者設定，不是帳單；實際有付資料費就要改這個值（見 `net_alpha_attribution_service.py` 同一個鍵）。

```bash
docker exec advisor_prod_db psql -U postgres -d advisor_prod -At -c "select key, value from settings where key='monthly_data_subscription_cost_usd'"
```

**10-15 之後花費下降：確認是用量真的下降，原因未定。**
- 內部用量日誌 `llm_usage_logs` 的每日呼叫數，10-14 前約 900–1100 次，10-15 起降到約 100–300 次，是一個台階，不是漸降。
- 排程沒變：`sentinel_tick`、`ingest_rss_feeds`、`analyze_ingested_event` 等 beat 任務的執行次數前後相近。所以不是排程停擺。
- 台階主要來自 `agent_name='budget_aware_router'`：前期每日約 570–680 次小呼叫（每次約 150 token），10-15 當天降到 0，之後每日約 0–150。這個名稱是 `get_resilient_gateway` 的預設 agent 名（`budget_aware_model_router.py` 約 267 行），代表沒有自己名字的呼叫端；呼叫端有 `council_tier_router.py` 與 `confidence_compositor_service.py`。
- CIO（smart 級，每次最貴）的呼叫數從每日約 40–60 次降到 0–26 次，週末與凍結日接近 0。
- 同日（10-13 到 10-15）合併了 Phase 40–55 的大批功能（含 `budget_aware_model_router.py` 被改動的 commit bd84dcc1），也剛好是 `run_litellm_spend_collect` 開始有紀錄的時間。**我沒有證據指出哪一個改動造成台階**；只知道不是排程。[推論：呼叫端的行為在該批合併後改變]
- 因此「花費已經降下來」可以信（兩個獨立來源一致：內部呼叫數與 LiteLLM 計費），但「會維持」沒有依據，因為原因不明。
- 另一個警訊：10-15 前的 `llm_real_cost_daily` 是否由當時的收集器寫入未驗證。記憶中 10-15 前的快照有不可靠紀錄；本 DD 對 10-09 到 10-14 的金額只當相對規模。

**仍未查：** K1 單位寫「滾動 12 月」，watchdog 實作是 30 日年化，差異未評估。

## 5b B 案具體方案（待你選）

目標：連續 7 日實付 ≤ 每日 $0.10（年化約 $36，留約 $13 給資料與手續費），解除日約 11-20。現況：近 7 日均約 $0.14，近 14 日均約 $0.27。要降的幅度，以近 7 日均算約 30%，以近 14 日均算約 60%。

成本結構（內部日誌的相對占比，10-23 到 10-29，**不是計費金額**：內部估價約為 LiteLLM 實付的三倍以上）：CIO 約一半，`budget_aware_router` 約 14%，Risk 約 9%，其餘八個代理各約 3–5%。

| 槓桿 | 做法 | 預估降幅（推論，依占比） | 風險 |
|---|---|---|---|
| L1 凍結時不開會 | 憲章凍結期間，不為會被擋下的買單召開 CIO／Council 辯論；跳過要帶標記（不靜默），報告顯示「凍結跳過」 | 最大。CIO 占一半，可能降 30–50% | R2（排程與決策路徑，須符合約束 #0）；與 DD-2026-1029 的買單閘門選項相依：閘門修好後這些辯論才確定無用 |
| L2 呼叫端命名並設日上限 | 為用預設名 `budget_aware_router` 的呼叫端補自己的 agent 名；LLM 設每日美元上限，用完就跳過並標記 | 不直接省錢，但讓 10-15 那種台階看得見、讓上限可執行 | R2 |
| L3 CIO 降級 | 例行檢視用 fast 級，僅高波動或持倉風險事件用 smart | 約 10–25% | R2（prompt／tier 路由）；品質風險要先看回放 |
| L4 快取 | compositor 小呼叫的短期結果快取 | 約 5–10% | R1 |

建議：先做 L1 與 L2，不動模型等級。L1 砍的是凍結期間本來就不會產生訂單的呼叫，對決策品質沒有損失；L2 讓之後的花費變動看得見。L3 動到決策品質，等有績效資料再說。L1 預估可把近 7 日均壓到約 $0.08，但這是依占比的估算，實作 PR 的驗收要用實付數字確認。
